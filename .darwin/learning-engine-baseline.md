## 诊断：三个真实短板

**1. 失败模式编码（dim3 = 3 分）— 最严重**

skill 假设了理想输入：用户说清了目的、项目有源码、能抽到参考条目。三种常见偏离全部没有分支：

- 用户只说「学一下 XX」不说目的 → 现在会默认按「上手+二开混合」处理，这正是 HolmesGPT 那次的错误
- 项目是纯 SaaS / 闭源 → 没有源码，只能靠文档，抽取策略完全不同
- 项目太小（如 `jq`）→ 抽出来的参考条目只有 5 条，页面显得空

**2. 检查点设计（dim4 = 1.2 分）— 最严重**

`SKILL.md` 里写「如果用户已经说清楚了，不要重复问」，但没有任何视觉标记。实测中 with_skill 的子 agent 确实问了问题，但那是它自己判断的，不是 skill 强制的。换一个 agent 可能直接开始生成。

**3. 反例与黑名单（dim9 = 2.4 分）**

有写作层面的反例（AI 腔对照表），但没有**流程层面**的红灯清单。这次开发中真实踩过的坑——写死项目名、进度 key 不隔离、行内代码 nowrap 撑爆布局——没有一个被编码进 skill 作为「绝对不要」。

## 结论

skill 的核心价值成立：三个 prompt 里 with_skill 都产出了可验证的计划（来源指回、参数从签名来、分类不预设）。但**流程韧性不足**——它只在顺利路径上可靠。

下轮优化优先级：dim3（+3.6 可拿）> dim4（+4.8 可拿）> dim9（+3.6 可拿）。
