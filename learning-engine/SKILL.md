# 学习引擎

## 这个 skill 做什么

输入一个项目名和学习目的，输出**一个 HTML 文件**：分阶段、每步一屏、事实带来源、
右侧常驻参数速查。使用者读这一页就能建立全景，细节再回官方文档查。

不是写综述，不是写教程。是**替某个具体的人，把某个具体项目的知识，按他自己会用的顺序排好**。

## 第一步：先问清三件事

**🔴 CHECKPOINT · 动手前停下**

三个答案没拿到（或无法从上下文推断）之前，不要开始抽事实，不要写任何内容。
先问，拿答案，再继续。

1. **目的**：一周内上手用 / 二次开发 / 选型对比 / 讲给别人听
   - 上手 → 装、配、最常见的 20%、坑
   - 二开 → 架构、扩展点、源码地图
   - 选型 → 生态位、边界、天花板、对比
   - 讲清楚 → 核心概念、设计取舍

2. **环境**：本地有仓库吗？能跑吗？看的是哪个版本？
   - 本地有仓库：直接读源码，最准
   - 只能看远程：clone 或读文档站
   - 能跑：优先实测，实测 > 源码 > 文档

3. **深浅**：一晚上够用，还是准备泡一周
   - 这决定每关放几步、每步写多细

如果用户已经在本轮对话里说清楚了，直接用，不要重复问。判断标准是**能写出阶段划分的理由**——写不出来说明信息不够，回去问。

<details>
<summary><b>用户不配合 / 说不清时怎么办</b></summary>

| 情况 | 一线处理 | 仍不行就兜底 |
|---|---|---|
| 用户只说「学一下 XX」 | 问一句「用 / 二开 / 选型？」 | 默认按**上手**做，把原理压成各关末尾的一节；在页面开头的 intro 里写明「按上手目的生成」 |
| 用户说「随便」/「你看着办」 | 不再追问，直接说明你要按什么假设做，让用户有机会打断 | 同上，且把假设写进 intro |
| 用户没说版本 | 本地仓库读 `git rev-parse`；远程读最新 release tag | 用最新稳定版，并在页面底部写明「基于 x.y.z」 |

</details>

## 第二步：抽事实，不要凭记忆写

**🔴 CHECKPOINT · 版本没查到，不许开始**

按优先级取证据：

```
实测输出  >  源码  >  官方文档  >  二手资料
```

冲突时以源码为准，并在正文里说明差异。

### 先钉版本，再谈别的

**动笔第一件事：查出版本号，写进页面。**

```bash
git describe --tags --always        # git 仓库
grep -m1 version pyproject.toml     # Python
node -p "require('./package.json').version"   # Node
grep -m1 '^version' Cargo.toml      # Rust
```

版本号必须出现在两处：页面 intro，以及每一条源码来源的旁边。原因很直接——**API 断代、参数增删、默认值变化都跟版本绑定**。写「LangChain 的 `create_agent`」而不说是 0.x 还是 1.x，读者按旧教程操作会全线报错。

版本查不到时（无 tag、无 manifest），**明说「版本未知」**，并把「原理」关降级为「已知设计取舍」，不要假装能讲实现。

### 先钉不可逆分叉

有些决策选错了要整页重做。写内容之前，把它们列出来逐条定：

| 分叉类型 | 例子 | 选错的后果 |
|---|---|---|
| **大版本断代** | LangChain 0.3 `AgentExecutor` vs 1.x `create_agent` | 参数表、术语、示例全部作废 |
| **两套并存 API** | pydantic v1 vs v2、React 18 vs 19 | 一半内容对不上 |
| **部署形态** | 单机 CLI vs 服务端 vs Operator | 阶段划分完全不同 |
| **核心场景** | 用它当库调用 vs 当独立服务跑 | 整页重心偏移 |

处理方式：先自己判断出默认值（通常是「最新稳定版 + 最常见的形态」），写明「本页基于 X，如果你用的是 Y，请对照官方文档」，而不是卡在这里等用户回答。

<details>
<summary><b>抽不到源码时怎么办</b></summary>

| 情况 | 一线处理 | 仍不行就兜底 |
|---|---|---|
| 闭源 SaaS，无源码 | 只走文档路径，来源全部标 `doc` | 在页面顶部注明「本页全部依据官方文档，无法交叉验证源码」，并减少「原理」关的深度 |
| 仓库太大（>10 万行） | 只读入口文件 + 公开 API 面，不读内部实现 | 原理关改成「源码地图」——告诉用户该去哪个目录，不试图讲清实现 |
| 项目太老或已停止维护 | 读最后一次 release 的对应 tag | 在页面注明「上游已停止维护」，并提示读者自行评估 |
| 文档站打不开 | 读 README / 仓库内 docs 目录 | 只用源码，来源全部标 `code`，并在 intro 说明 |

</details>

### 按目的决定读到多深

**这是最容易做错的一步。** 读源码不等于学得更好。

| 目的 | 该读什么 | **不该读什么** |
|---|---|---|
| 上手用 | CLI/API 定义、`--help` 输出、快速开始、常见坑 | 内部实现、设计模式、性能路径 |
| 二次开发 | 架构分层、扩展点、公开 API 面、模块边界 | 逐行实现、历史提交 |
| 选型 | 能力边界、天花板、对比项、限制 | 安装步骤、命令全集 |
| 讲清楚 | 核心概念、设计取舍、演进原因 | 参数清单 |

**上手场景反例**（真实踩过）：为了讲清 ripgrep 的参数，去读它的 `Flag` trait 实现，得出「104 个 `impl Flag for`、7 个 Category」——这对二次开发有价值，对「一周上手」是噪音。**用户要的是怎么用，不是它内部怎么实现。**

判断方法：如果这条事实不能改变用户的操作方式，就不属于上手内容。

要抽的东西：

| 项目类型 | 抽什么 | 怎么抽 |
|---|---|---|
| Python CLI | 命令、参数、默认值 | `grep -n "typer.Option\|@.*command\|add_argument"` |
| Go CLI | flag、子命令 | cobra `cmd.Flags()`、`PersistentFlags()` |
| Node CLI | 选项 | commander `.option()`、yargs `.options()` |
| 库/SDK | 公开 API、构造参数 | 导出符号 + 类型定义 |
| 服务 | 配置项、环境变量、端点 | config schema、`os.environ`、路由表 |
| 任何项目 | 环境变量 | `grep -rn "environ\|getenv\|ENV\["` |
| 任何项目 | 文件路径 | 默认值常量、`expanduser` |
| 任何项目 | **有没有 CLI** | `ls cli/ cmd/`、`grep -rn "console_scripts\|\[project.scripts\]"` |

**参数表只能从签名长出来。** 手写参数表是错误来源第一位。

**不要假设项目没有 CLI。** 很多库会附带一层薄 CLI（FastAPI 有 `fastapi/cli.py` 转发 `fastapi-cli`，提供 `dev`/`run`）。grep 过再下结论，否则会漏掉整个分类，还会在正文里写出「这个项目没有命令行」这种硬错。

**完成判据**：每个阶段至少能填满 3 条来源；总参考条目少于 5 条时，说明这个项目不适合做完整读本，改做「单页速览」。

详细抽取命令见 `references/extraction.md`。

## 第三步：设阶段

**不要固定四关。** 关数由项目复杂度决定，阶段名由项目自身结构决定。

判断依据是「学习者依次要回答的问题」：

1. 这东西是什么、为什么存在
2. 我怎么让它跑起来
3. 它内部怎么做到的
4. 边界在哪、细节怎么查

每个问题**要不要单独成关，看项目的复杂度**：

- 简单工具（jq、ripgrep）：两个问题就够，两关
- 中等框架（LangChain）：抽象 → 最小链 → 组合 → 调试 → 部署，五关
- 大型系统（K8s）：概念 → 最小可用 → 控制面 → 网络存储 → 排障，五关

**学习目的会改变关卡**：

- 为了用 → 不要原理关
- 为了二开 → 原理要拆成两到三关
- 为了选型 → 加一关对比，砍掉安装细节

**完成判据**：用一句话写出阶段划分的理由。理由写不出来，说明还没想清楚，回第二步。

<details>
<summary><b>阶段划分的三种偏离</b></summary>

| 情况 | 一线处理 | 仍不行就兜底 |
|---|---|---|
| 项目太简单，凑不出 2 关 | 合并成 1 关，页面就叫「全貌」 | 参考条目 < 8 条时，改输出**单页速览**而非读本：只保留一屏，不分关 |
| 项目太复杂，超过 7 关 | 拆成两个页面，按「用法」和「原理」分开 | 在 intro 说明这是第一部分，并指明第二部分覆盖什么 |
| 用户要的角度和默认冲突（如想学原理但项目无源码） | 明确告诉用户「这个项目只能学到用法层面」 | 把原理关改成「已知的设计取舍」——引用官方博客/设计文档，标明来源不可验证 |

</details>


## 第四步：写内容

每条事实都必须挂来源角标。写法见 `references/writing.md`。

硬规则：

- **数字必须能数出来**。标题写"三种方式"，正文就得恰好三条。
- **术语首次出现给定义**。不要假设读者知道 toolset、middleware、operator 是什么。
- **配置入口首次出现必须点名类型**：`--flag` 是命令行参数，`UPPER_SNAKE` 是环境变量，
  `lower_snake` 是配置文件字段。不允许写"可以用 X 改"而不说 X 是什么。
- **标出 experimental / deprecated**。官方标了就必须原样标。
- **不写没有根据的量化**。"动辄上万 token"这种，要么有实测，要么删。
- **示例代码标明是示意还是真实输出**。

**删掉 AI 腔**：

| 别写 | 改成 |
|---|---|
| 值得注意的是、换句话说、总的来说 | 直接说结论 |
| 不只是 X，而是 Y | X 和 Y 分开讲 |
| 非常实用、极其重要 | 说清什么场景下有用 |
| 每段结尾都总结一遍 | 只在真需要回收时总结 |
| 强行对仗的四字标题 | 用具体名词 |
| 到处加粗 | 一页最多两处 |

## 第五步：渲染

用 `assets/template.html`，把数据注入 `const DATA = {{DATA}};`。

数据格式：

```js
{
  slug: "项目短标识",          // 用于 localStorage 隔离，必填且唯一
  project: "项目名",
  subtitle: "目录页标题",
  intro: "目录页导语",
  sources: {
    key: { kind: "code"|"doc"|"run", path: "...", line: 123, href: "...", why: "支持了哪个说法" }
  },
  stages: [
    { name: "阶段名", desc: "一句话", steps: [
      { title: "页标题", blocks: [...], sources: ["key1","key2"] }
    ]}
  ],
  reference: [
    { cat: "分类名", key: "键名", short: "一句话", doc: "详情 HTML" }
  ]
}
```

块类型：`p` `h3` `ul` `ol` `code` `note` `warn` `table` `kv` `split` `opts`

正文里 `{{1}}` 渲染成角标，序号对应本页 `sources` 数组下标 +1。

**分类从数据推出来**（`REF_CATS` 由 `reference` 里的 `cat` 去重生成），不要预设。
项目没有 CLI 就没有"命令"分类，不要留空分类。

**色相、关卡数、每关步数都不写死**，模板里没有这些常量。

## 第六步：机器校验

**🔴 CHECKPOINT · 校验不通过不许交付**

落盘前必须跑。见 `references/checks.md`。

最低要求：

- 每个 `path:line` 打开后内容对得上
- 每个 `{{n}}` 的 n 不超过该页 sources 长度
- 标题里的数字等于实际条目数
- 所有页面能渲染，零 JS 报错
- 窄屏无横向溢出
- 没有无来源的事实陈述

```bash
python3 references/verify.py output.html
```

<details>
<summary><b>校验失败怎么办</b></summary>

| 失败项 | 一线修复 | 仍失败就兜底 |
|---|---|---|
| 角标越界 | 检查该页 sources 数组是不是漏了条目 | 删掉该角标，把句子改成不需要来源的表述 |
| 某页无来源 | 补 sources | 如果这页本来就是纯导航/纯过渡，考虑合并到相邻页 |
| 标题数字对不上 | 改正文条目数，或改标题 | 改成不带数字的标题（「几种常见方式」→「常见方式」） |
| 来源 key 不存在 | 补 `sources` 字典 | 删掉该 key 引用 |
| 页面渲染报错 | 看 console 定位 | 回退到上一个可用版本，单独修那一处 |
| 行号对不上 | 重新 grep 定位 | **去掉 line，只留文件名**——行号是最大漂移源，不如不要 |

</details>

## 第七步：人工通读

机器查不出"读起来像 AI 写的"。自己从头读一遍，专门找：

- 有没有句子在重复上一句的意思
- 有没有段落可以整段删掉而不损失信息
- 有没有解释了三遍同一个概念
- 加粗用了多少次（一页超过两处就砍）
- 有没有哪句是"正确的废话"

## 流程红灯 · 绝对不要做

这些是真实踩过的坑，每一条都导致过返工。

| # | 不要做 | 为什么 | 改成 |
|---|---|---|---|
| 1 | **把项目名/命令名写进模板正则** | 换个项目就抽不到内容，而且不会报错，只会静默失效 | 靠 `reference` 的 key 反向匹配，模板里不出现任何项目名 |
| 2 | **进度存储用全局 key** | 生成第二个项目时，两边进度串台 | 每个项目唯一的 `slug`，key 拼上 slug |
| 3 | **行内 code 加 `white-space:nowrap`** | 长变量名（`WEBHOOK_URL / WEBHOOK_METHOD`）会撑破布局，实测撑爆 3 页 | `overflow-wrap:anywhere`，代码块单独 `max-width:100%` |
| 4 | **入场动画从 `opacity:0` 开始** | 动画没跑完内容就不可见，截图和低性能设备上整页空白 | 只做位移，不改透明度 |
| 5 | **行内 code 样式不限定作用域** | `.opt code{...}` 会污染 `pre code`，代码块换行全丢，三行命令挤成一行 | 选择器精确到 `.opt .od code` 这种层级 |
| 6 | **参数表凭记忆手写** | 写出过官方文档里没有的选项（`--documents` 只在一条命令上有） | 只从签名生成，逐条回查 |
| 7 | **说「可以用 X 改」不说 X 是什么** | 新手分不清环境变量/CLI 参数/配置字段，改完没效果 | 首次出现点名：环境变量 / 命令行参数 / 配置文件字段 |
| 8 | **标题写数量不核对** | 写「三种东西」正文四条 | 落盘前数一遍，`verify.py` 会抓 |
| 9 | **为了凑形态造数据** | 空分类、无对位条目会让整页显假 | 抽到什么写什么，没有就留白并说明 |
| 10 | **不确定就写「大约」「通常」** | 无依据的量化比不写更糟 | 要么有实测，要么删掉 |


## 模块开关

| 模块 | 默认 | 什么时候开 |
|---|---|---|
| 正文 + 来源 | 必选 | — |
| 参考手册 | 有可抽取内容时开 | `reference` 非空 |
| 右侧速查栏 | 有可抽取内容时开 | 同上 |
| 自测题 | 关 | 用户明确要检验掌握程度 |
| 破坏实验 | 关 | 用户有真实环境且愿意折腾 |
| 间隔复习 | 关 | 用户明确说要用很久 |

不要替用户决定砍掉后三项，也不要默认打开。问一句。

## 已知限制

- **行号会漂**。上游一改就失效。解决办法：钉 commit，或只写文件名不写行号。
  默认用 `href` 指向文件而非行号锚点，`line` 仅作参考。
- **右侧速查靠 key 反向匹配正文**，会漏（正文用了别名）也会误（短词撞车）。
  匹配不到时右侧留白是正常的，不要造内容填。
- **非 Python 项目没有现成抽取配方**。Go、Rust、TS 见 `references/extraction.md`，
  没有的话自己 grep，别猜。

## 参考文件

- `references/extraction.md` — 各类项目的抽取命令
- `references/writing.md` — 正文写法、来源标注、反例
- `references/checks.md` — 机器校验清单和脚本
- `assets/template.html` — 页面模板（含渲染引擎和全部样式）

## 模板不写死的东西

这些都由数据决定，改数据就能变，不用改模板：

| 项 | 由什么决定 |
|---|---|
| 关数 | `stages.length` |
| 每关页数 | `steps.length` |
| 参考分类 | `reference` 里 `cat` 去重，没有就自动不显示 |
| 参考条目数 | `reference.length`，为 0 时按钮自动隐藏 |
| 进度隔离 | `slug`，每个项目必须不同 |
| 页面标题、品牌名 | `project` |
| 有无右侧速查栏 | 有 `reference` 才显示内容 |

**不要为了凑某个形态去造数据。** 项目没有 CLI 就没有"命令"分类，参考条目只有三条
就写三条。空分类、凑数条目会让整页显得假。
