# 学习引擎

## 这个 skill 做什么

输入一个项目名和版本，输出**一套 HTML 读本**：分册、分阶段、每步一屏、事实带来源、
右侧常驻参数速查。

### 它是第一入口，不是索引

**学这个技术，先看这套读本。** 目标是把所有东西都在这里解决掉——遇到问题先在这里找，
找不到才去官方文档。

| | 官方文档 | 这套读本 |
|---|---|---|
| 是什么 | **补充**。这里遗漏时才去查 | **第一入口**。应该先看这里 |
| 组织方式 | 按功能模块，写给已经懂的人 | 按学习顺序，写给正要懂的人 |
| 覆盖范围 | 全，但散 | **也应该全**，且集中 |
| 概念和细节 | 混在一起 | 分层，深的往后放 |
| 参数 | 散在各页 | 一页速查，按用途分组 |
| 踩坑 | 通常不说 | 单独成节 |
| 进度 | 无 | 左目录标已读 |

**唯一不管的是版本更新。** 本文档只对写它时的那个版本负责，明确写出版本号。
之后项目怎么变，不在这套文档的责任范围内——读者应该知道自己在用一个特定版本的说明。

**所以内容标准不是「够用」，是「有没有遗漏」**：

- 所有公开能力（命令、参数、API、配置项、环境变量）都要有
- 每个能力至少有一个能跑的例子
- 常见错误每个都要有对应解法
- 判断标准：读者遇到问题来这里查，**查不到就是缺陷**

官方文档只在两种情况下需要：这套读本还没覆盖到，或者你用的是别的版本。

## 第一步：先定层次，不是选方向

**🔴 CHECKPOINT · 动手前停下**

三个答案没拿到（或无法从上下文推断）之前，不要开始抽事实，不要写任何内容。
先问，拿答案，再继续。

### 1. 默认全要

既然目标是「先看这里就能解决」，**默认四个层次全要**。不用问用户要哪层，
只在明显可以省略时才省（比如用户明说「我一晚上就得用上」）。

| 层 | 回答什么问题 | 放在哪 |
|---|---|---|
| **L1 用** | 我怎么让它跑起来 | 第一册 |
| **L2 懂** | 它内部怎么做到的 | 第一册后半，或第二册 |
| **L3 改** | 我要动它该从哪下手 | 第二册 |
| **L4 选** | 它和别的比强在哪 | 第二册末 |

**层次决定顺序和篇幅，不决定写不写。** 自足要求所有层都在，只是浅的在前、深的在后。

**分册是常态，不是例外。** 册数由**清点出的能力项数**决定，不是拍脑袋定的：

| 清点总数 | 册数 | 单册页数 |
|---|---|---|
| < 60 项（jq、ripgrep） | 1 册 | 15–25 页 |
| 60–200 项（中型 CLI/库） | 2–3 册 | 20–40 页 |
| 200–500 项（LangChain、FastAPI） | 3–4 册 | 25–40 页 |
| 500+ 项（Docker、K8s） | 5–8 册 | 25–40 页 |

**不要为了「好看」把册数压少。** Docker 有 818 项，压成 2 册的结果是每册 60 页、
每页塞 7 个参数——读的人会放弃。册多不是缺点，册里找不到东西才是。

**单册的硬上限是 40 页。** 超过就再拆一层。下限没有——15 页的一册也是合格的一册。

### 2. 环境：本地有仓库吗？能跑吗？看的是哪个版本？

- 本地有仓库：直接读源码，最准
- 只能看远程：clone 或读文档站
- 能跑：优先实测，实测 > 源码 > 文档

### 3. 深浅：一晚上够用，还是准备泡一周

这决定每关放几步、每步写多细，也决定要不要分册。

如果用户已经在本轮对话里说清楚了，直接用，不要重复问。判断标准是**能写出阶段划分的理由**——写不出来说明信息不够，回去问。

### 多轮交付

自足不等于一次交付完。完整的四层内容通常是 30–120 页，必须分轮做。

**第 1 轮的关键交付是 `coverage.md`，不是页面。**
用户看到 40% 的覆盖度会以为你做了一半就交差；但如果同时给出一份完整清点清单
（「总共 104 项，这册写了 45 项，剩下 59 项在第二册」），性质就变成有计划的连载。

轮次安排、每轮交付物、覆盖度目标见 `references/coverage.md` 的「多轮交付」一节。

<details>
<summary><b>分册的切分方式</b></summary>

按层切，不按内容量切。同层的内容放在同一册，读者才知道这册是干什么的。

| 覆盖层 | 册名 | 关数 |
|---|---|---|
| L1 + L2 | 用与懂 | 5–6 |
| L3 | 改 | 3–4 |
| L4 | 选 | 2–3 |

项目特别大的（K8s 这个量级），L1 和 L2 也要拆开：

| 覆盖层 | 册名 |
|---|---|
| L1 | 用起来 |
| L2 | 怎么做到的 |
| L3 | 改哪里 |
| L4 | 和别的比 |

**单册不要超过 40 页。** 超过说明切分粒度太粗，再拆一层。

</details>

<details>
<summary><b>用户不配合 / 说不清时怎么办</b></summary>

| 情况 | 一线处理 | 仍不行就兜底 |
|---|---|---|
| 用户只说「学一下 XX」 | 问一句「只用，还是要连原理一起？」 | 默认 **L1 + L2**，并在 intro 写明「含原理层，如果只想上手可以跳过第 3 关之后」 |
| 用户说「随便」/「你看着办」 | 不再追问，直接说明你要按什么假设做，让用户有机会打断 | 同上，且把假设写进 intro |
| 用户说「多多益善」「越深越好」 | 按全四层处理，但**先只交付第一册** | 在 intro 写明这是第一册，第二册覆盖什么 |
| 用户没说版本 | 本地仓库读 `git rev-parse`；远程读最新 release tag | 用最新稳定版，并在页面底部写明「基于 x.y.z」 |

</details>


## 第二步：抽事实，不要凭记忆写

**🔴 CHECKPOINT · 版本没查到，不许开始**

按优先级取证据：

```
实测输出  >  源码  >  官方文档  >  二手资料
```

冲突时以源码为准，并在正文里说明差异。

### 先钉版本，再谈别的

**动笔第一件事：查出版本号，写进页面。**

```bash
git describe --tags --always        # git 仓库
grep -m1 version pyproject.toml     # Python
node -p "require('./package.json').version"   # Node
grep -m1 '^version' Cargo.toml      # Rust
```

版本号必须出现在两处：页面 intro，以及每一条源码来源的旁边。原因很直接——**API 断代、参数增删、默认值变化都跟版本绑定**。写「LangChain 的 `create_agent`」而不说是 0.x 还是 1.x，读者按旧教程操作会全线报错。

版本查不到时（无 tag、无 manifest），**明说「版本未知」**，并把「原理」关降级为「已知设计取舍」，不要假装能讲实现。

**版本边界是免责声明，必须写在页面上**：

> 本读本基于 `<tool> x.y.z`（`<commit 或发布日期>`）。
> 之后版本的变化不在这套文档的范围内。如果你用的不是这个版本，
> 请以官方文档为准，并注意参数和行为可能已经改变。

这段话放在 intro 里，不要藏在页尾。理由：读者需要一开始就知道自己在看哪个版本的说明。
写「最新版」是错的——「最新」在写完的第二周就不成立了。

### 先钉不可逆分叉

有些决策选错了要整页重做。写内容之前，把它们列出来逐条定：

| 分叉类型 | 例子 | 选错的后果 |
|---|---|---|
| **大版本断代** | LangChain 0.3 `AgentExecutor` vs 1.x `create_agent` | 参数表、术语、示例全部作废 |
| **两套并存 API** | pydantic v1 vs v2、React 18 vs 19 | 一半内容对不上 |
| **部署形态** | 单机 CLI vs 服务端 vs Operator | 阶段划分完全不同 |
| **核心场景** | 用它当库调用 vs 当独立服务跑 | 整页重心偏移 |

处理方式：先自己判断出默认值（通常是「最新稳定版 + 最常见的形态」），写明「本页基于 X，如果你用的是 Y，请对照官方文档」，而不是卡在这里等用户回答。

<details>
<summary><b>抽不到源码时怎么办</b></summary>

| 情况 | 一线处理 | 仍不行就兜底 |
|---|---|---|
| 闭源 SaaS，无源码 | 只走文档路径，来源全部标 `doc` | 在页面顶部注明「本页全部依据官方文档，无法交叉验证源码」，并减少「原理」关的深度 |
| 仓库太大（>10 万行） | 只读入口文件 + 公开 API 面，不读内部实现 | 原理关改成「源码地图」——告诉用户该去哪个目录，不试图讲清实现 |
| 项目太老或已停止维护 | 读最后一次 release 的对应 tag | 在页面注明「上游已停止维护」，并提示读者自行评估 |
| 文档站打不开 | 读 README / 仓库内 docs 目录 | 只用源码，来源全部标 `code`，并在 intro 说明 |

</details>

### 穷尽，不是挑选

**先做一次全量清点，再决定怎么写。**

抽事实的第一步不是挑重点，是把所有公开能力列出来，记进 `coverage.md`。
清点命令、`coverage.json` 格式、覆盖度算法见
`references/coverage.md`。

最低要求：

- `coverage.md` 每项标 ✅ / 📝 / ❌，`❌` 必须写原因
- 覆盖度 ≥ 95% 才能交付
- **不存在「上手场景不读原理」这种豁免**——层次决定顺序和篇幅，不决定写不写

反例（真实踩过）：为了讲清 ripgrep 参数，agent 主动决定「104 个旗标只取 30 个」。
按自足标准这是缺陷——104 个都该进参考栏，只是分组呈现、正文只展开高频的。

要抽的东西：

| 项目类型 | 抽什么 | 怎么抽 |
|---|---|---|
| Python CLI | 命令、参数、默认值 | `grep -n "typer.Option\|@.*command\|add_argument"` |
| Go CLI | flag、子命令 | cobra `cmd.Flags()`、`PersistentFlags()` |
| Node CLI | 选项 | commander `.option()`、yargs `.options()` |
| 库/SDK | 公开 API、构造参数 | 导出符号 + 类型定义 |
| 服务 | 配置项、环境变量、端点 | config schema、`os.environ`、路由表 |
| 任何项目 | 环境变量 | `grep -rn "environ\|getenv\|ENV\["` |
| 任何项目 | 文件路径 | 默认值常量、`expanduser` |
| 任何项目 | **有没有 CLI** | `ls cli/ cmd/`、`grep -rn "console_scripts\|\[project.scripts\]"` |

**参数表只能从签名长出来。** 手写参数表是错误来源第一位。

**不要假设项目没有 CLI。** 很多库会附带一层薄 CLI（FastAPI 有 `fastapi/cli.py` 转发 `fastapi-cli`，提供 `dev`/`run`）。grep 过再下结论，否则会漏掉整个分类，还会在正文里写出「这个项目没有命令行」这种硬错。

**完成判据**：`coverage.md` 里没有「既没写也没写原因」的项，且覆盖度 ≥ 95%。
判断「够不够」不看条数下限，看有没有遗漏。

参考条目少的项目（少于 20 条）通常意味着项目本身能力面窄，可以做单册；
但**不能因为条目少就跳过清点**——「少」和「没抽全」是两件事，靠 coverage 数字区分。

详细抽取命令见 `references/extraction.md`。

## 第三步：设阶段

**不要固定四关。** 关数由项目复杂度决定，阶段名由项目自身结构决定。

判断依据是「学习者依次要回答的问题」：

1. 这东西是什么、为什么存在
2. 我怎么让它跑起来
3. 它内部怎么做到的
4. 边界在哪、细节怎么查

每个问题**要不要单独成关，看项目的复杂度**：

- 简单工具（jq、ripgrep）：两个问题就够，两关
- 中等框架（LangChain）：抽象 → 最小链 → 组合 → 调试 → 部署，五关
- 大型系统（K8s）：概念 → 最小可用 → 控制面 → 网络存储 → 排障，五关

**学习层次会改变关卡**（层次可叠加，不要只按一层写）：

| 层次 | 关卡怎么变 |
|---|---|
| L1 用 | 不要原理关 |
| L1 + L2 | 原理拆成 2–3 关，紧跟在最小可用之后 |
| 加 L3 改 | 加「源码地图」和「扩展点」两关，通常独立成册 |
| 加 L4 选 | 加一关对比，砍掉安装细节 |

**「深入一点」指的是 L2，不是 L3。** 用户想看内部怎么做到的，不等于想改它。
搞混了会把读本写成源码分析报告。

**完成判据**：用一句话写出阶段划分的理由，并标明对应哪几层。理由写不出来，说明还没想清楚，回第二步。


<details>
<summary><b>阶段划分的三种偏离</b></summary>

| 情况 | 一线处理 | 仍不行就兜底 |
|---|---|---|
| 项目太简单，凑不出 2 关 | 合并成 1 关，页面就叫「全貌」 | 参考条目 < 8 条时，改输出**单页速览**而非读本：只保留一屏，不分关 |
| 项目太复杂，超过 7 关 | 拆成两个页面，按「用法」和「原理」分开 | 在 intro 说明这是第一部分，并指明第二部分覆盖什么 |
| 用户要的角度和默认冲突（如想学原理但项目无源码） | 明确告诉用户「这个项目只能学到用法层面」 | 把原理关改成「已知的设计取舍」——引用官方博客/设计文档，标明来源不可验证 |

</details>


## 第四步：建概念台账

**🔴 CHECKPOINT · 台账没建完，不许动笔写正文**

这是防止「前面看不懂后面」的唯一可靠办法。写完再检查只是补救，
**动笔前把概念顺序排好才是根治**。

### 为什么必须先建

人会不自觉地在讲 A 的时候提到 B，因为写的人已经懂了。
读者按顺序读，第一次遇到 B 时没有任何上下文，就卡住了。

**动笔前先回答：读者按照我的顺序读，每一页用到的概念，是不是都已经在前面讲过？**

### 怎么建

把整个读本里**所有会出现的概念**列成一张表。概念包括：

- 专有名词（容器、镜像、命名空间、middleware）
- 命令与子命令（`docker run`、`docker volume create`）
- 配置项与环境变量
- 参数（常用且有理解门槛的）
- 缩写（OCI、ASGI、CRD）

对每个概念填四列：

| 概念 | 引入页 | 说明强度 | 后续使用页 |
|---|---|---|---|
| 镜像 | 1-3 | 完整（是什么 + 和容器的关系 + 图） | 2-2, 4-1, 4-2 |
| 容器 | 1-3 | 完整 | 全文 |
| 命名卷 | 5-1 | 完整 | 5-2, 6-3 |
| `--rm` | 2-5 | 完整 | — |
| overlay 网络 | 5-3 | 一句话带过 | — |

**「引入页」必须是这一页的主题**，不是顺带提一句。
判断标准：这一页的小标题或标题里能出现它。

### 三条硬规则

**规则 1：引入必须先于使用。**

```
✗ 2-2 用 --rm 但不解释，2-5 才讲
✓ 2-5 讲 --rm，之后的页面才用它
```

`order.py` 会检查这一条。但**不要靠它**——它只能抓「标题里出现过」的术语，
抓不到纯叙述里的概念。写的时候就要守住。

**规则 2：一个概念只引入一次。**

第一次出现的地方讲透（是什么、为什么需要、长什么样），后面只调用不复述。
如果在三个地方各解释一遍，说明台账没建好。

**规则 3：单页最多引入 4 个新概念。**

超过 4 个，读者一页里要装太多东西。要么拆页，要么把某个概念挪到后面。

### 台账放在哪

写进 `content.json` 同目录的 `concepts.md`，人可读。格式：

```markdown
# 概念台账 · Docker

| 概念 | 引入页 | 说明强度 | 后续使用 |
|---|---|---|---|
| 镜像 | 1-3 | 完整：只读模板 + 分层 | 2-2, 4-1 |
| 容器 | 1-3 | 完整：镜像 + 可写层 | 全文 |
| 命名卷 | 5-1 | 完整：位置、用途、与绑定挂载对比 | 5-2, 6-3 |
| `-v` | 5-1 | 完整：语法、坑 | 5-2, 6-3 |
| `--mount` | 5-2 | 完整：与 -v 的差别 | — |
```

不必写「后续使用」的精确页码，写个大概范围就够——它的作用是让你自己看清顺序，
不是给机器读的。

### 建台账的顺序

1. **先列概念清单**，不排序。想到什么写什么。
2. **标出前置关系**：B 依赖 A，就把 A 放到 B 前面。
   ```
   volume ← 挂载 ← 数据持久化 ← 容器删除会丢数据
   ```
3. **按章分配**：哪个概念属于哪一章，由「它解决什么问题」决定，
   不是由「它在官方文档的哪一节」决定。
4. **反查一遍**：假设自己是第一次接触这个项目的人，
   从第 1 页读到最后一页，每一页有没有看不懂的词。

### 写正文时对照台账

每写一页，先看一眼：**这页会用到哪些概念？它们都在前面吗？**

用到但前面没有的，只有两种处理：

- 挪到这一页来引入（这一页就讲它）
- 或者换个说法绕开（用已有概念描述）

**不允许「先用了再说，后面会讲」。**

## 第五步：写内容

**每写一页，先对照概念台账。** 这页要用到的概念，都在前面讲过了吗？
不在 —— 要么挪到这页来引入，要么换个说法绕开。

写完一整章，回读一遍：假设自己只读过前面的章节，这一章有没有看不懂的地方。

每条事实都必须挂来源角标。写法见 `references/writing.md`。

### 每页的结构顺序

一页之内也要由浅入深。固定用这个顺序：

1. **这页解决什么问题**（第一段，会变成导语）
2. **最具体的例子**（一条命令、一张图、一个表）—— 先让读者看到东西
3. **它怎么做到的**（机制解释）
4. **坑和边界**（旁注或列表）
5. **和其他东西的关系**（对比表，可选）

**不要反过来。** 先讲机制再举例，读者会不知道你在说什么。

### 硬规则：

- **「建议」是好的，前提是给出具体值**。`建议把 --max-steps 设在 15–20`
  是好句子；`建议根据情况调整` 是空话。区别在于有没有替读者做决定。
- **数字必须能数出来**。标题写"三种方式"，正文就得恰好三条。
- **术语首次出现给定义**。不要假设读者知道 toolset、middleware、operator 是什么。
- **配置入口首次出现必须点名类型**：`--flag` 是命令行参数，`UPPER_SNAKE` 是环境变量，
  `lower_snake` 是配置文件字段。不允许写"可以用 X 改"而不说 X 是什么。
- **标出 experimental / deprecated**。官方标了就必须原样标。
- **不写没有根据的量化**。"动辄上万 token"这种，要么有实测，要么删。
- **示例代码标明是示意还是真实输出**。

**删掉 AI 腔**：

| 别写 | 改成 |
|---|---|
| 值得注意的是、换句话说、总的来说 | 直接说结论 |
| 不只是 X，而是 Y | X 和 Y 分开讲 |
| 非常实用、极其重要 | 说清什么场景下有用 |
| 每段结尾都总结一遍 | 只在真需要回收时总结 |
| 强行对仗的四字标题 | 用具体名词 |
| 到处加粗 | 一页最多两处 |

## 第六步：渲染

**你只写 `content.json`，渲染交给 `build.py`。不要手写 HTML，不要改样式。**

```bash
python3 book.py check content.json    # 结构 + 文风 + 顺序，一次跑完
python3 book.py build content.json    # 校验通过才生成 index.html
python3 book.py all content.json      # 三步全跑
```

只有一个入口。`check` 失败即停，不用自己判断先修哪个。

文件分工：

| 文件 | 管什么 | 谁改 |
|---|---|---|
| `content.json` | 全部内容 | **你** |
| `assets/template.html` | 布局、样式、交互 | 不改 |
| `assets/schema.json` | 数据结构约束 | 不改 |
| `assets/lint-rules.json` | 文风规则（词表、阈值） | **可改**，见下 |
| `book.py` | 统一入口 | 不改 |
| `build.py` `lint.py` `order.py` | 单项检查 | 不改 |
| `references/verify.py` | 产物校验 | 不改 |

**样式一致性靠这个流程保证，不靠 AI 记忆。** 你只产出 JSON，
碰不到 HTML 和 CSS，所以每次长得一样。

**文风规则是数据，不是代码。** 觉得某个词该禁、某类加粗该少，
改 `assets/lint-rules.json` 就行，`lint.py` 不用动：

```json
{
  "existence": {
    "rules": [{"id":"ai-tone","tokens":["值得注意的是","赋能"],"message":"AI 腔"}]
  },
  "conditional": {
    "rules": [{"id":"vague-advice","first":["建议"],
               "need_one_of":["\\d","<code>"],"message":"建议没给具体值"}]
  }
}
```

### content.json 结构

完整 schema 见 `assets/schema.json`。必填字段：

```json
{
  "slug": "docker",
  "project": "Docker",
  "version": "Docker 29.8.2 · Compose 5.5.0",
  "subtitle": "单机容器",
  "intro": "本读本基于……覆盖……不覆盖……",
  "sources": {
    "key": {
      "kind": "run | code | doc",
      "path": "docker --version | /path/file.py | docs url",
      "line": 123,
      "href": "https://...",
      "why": "这条支持了正文的哪个说法"
    }
  },
  "stages": [
    {
      "name": "章名",
      "desc": "一句话说明这章解决什么问题",
      "steps": [
        {
          "title": "节标题",
          "sources": ["key1", "key2"],
          "blocks": [ ... ]
        }
      ]
    }
  ],
  "reference": [
    { "cat": "分类", "key": "键名", "short": "一句话", "doc": "<p>详情</p>" }
  ]
}
```

### 硬性约束（build.py 会拒绝）

| 约束 | 值 | 为什么 |
|---|---|---|
| `slug` | 小写字母数字连字符 | localStorage 隔离 |
| `intro` | ≥ 40 字 | 必须写清版本、范围、不覆盖什么 |
| 每页 `sources` | ≥ 1 条 | 没有来源的页面不允许 |
| 每页 `blocks` | ≤ 12 个 | 超过说明该拆页 |
| 表格 | 每行列数 = 表头数 | 渲染会错位 |
| 角标 `{{n}}` | n ≤ 来源数 | 否则指向不存在的依据 |
| `sources[].kind` | run / code / doc | 三选一 |

### 块类型

| type | 字段 | 什么时候用 |
|---|---|---|
| `p` | text | 正文段落 |
| `h3` | text | 分节小标题 |
| `ul` / `ol` | items | 列表。有顺序用 ol |
| `note` | text, label? | 要点旁注 |
| `warn` | text, label? | 警告旁注 |
| `code` | code, lang? | 代码块 |
| `table` | head, rows | 并列对比。有先后顺序用 ol |
| `kv` | items: [[k,v]] | 键值对，适合参数说明 |
| `split` | items: [{h,p}] | 2–4 个概念对比 |
| `opts` | items: [{title,desc,code,pick}] | 多个可选方案 |

正文里 `{{1}}` 渲染成上标角标，对应本页 `sources` 数组第 1 条。

### 分类从数据推出来

`reference[].cat` 去重生成分类，不要预设。项目没有 CLI 就没有「命令」分类，不留空分类。

## 第七步：机器校验

**🔴 CHECKPOINT · 校验不通过不许交付**

落盘前必须跑。见 `references/checks.md`。

最低要求：

- 每个 `path:line` 打开后内容对得上
- 每个 `{{n}}` 的 n 不超过该页 sources 长度
- 标题里的数字等于实际条目数
- 所有页面能渲染，零 JS 报错
- 窄屏无横向溢出
- 没有无来源的事实陈述

```bash
python3 book.py check content.json        # 结构 + 文风 + 顺序
python3 references/verify.py index.html --expect content.json   # 产物无损
```

两个都过，才算可以交付。

`verify.py` 不复跑业务检查（那些 `check` 已经做了）。它只查三件
**只有看产物才知道**的事：

1. `DATA` 能不能完整还原（注入过程有没有损坏数据）
2. HTML 结构有没有被内容破坏（`<script>` 闭合、占位符残留）
3. 覆盖率达标（可选 `--coverage`）

`--expect content.json` 做往返比对，是唯一能发现「生成时数据被改坏」的检查。

`order.py` 检查的是**概念依赖**：

- 前向引用（某页用了后面才讲的术语）
- 单页引入新概念超过 6 个
- 章首页纯概念、没有具体内容
- 章末页没有收尾

它只能抓到「标题里出现过」的术语，抓不到纯叙述里的概念。
**所以它是兜底，不是保证——真正的保证在第四步的台账。**

<details>
<summary><b>校验失败怎么办</b></summary>

| 失败项 | 一线修复 | 仍失败就兜底 |
|---|---|---|
| 角标越界 | 检查该页 sources 数组是不是漏了条目 | 删掉该角标，把句子改成不需要来源的表述 |
| 某页无来源 | 补 sources | 如果这页本来就是纯导航/纯过渡，考虑合并到相邻页 |
| 标题数字对不上 | 改正文条目数，或改标题 | 改成不带数字的标题（「几种常见方式」→「常见方式」） |
| 来源 key 不存在 | 补 `sources` 字典 | 删掉该 key 引用 |
| 页面渲染报错 | 看 console 定位 | 回退到上一个可用版本，单独修那一处 |
| 行号对不上 | 重新 grep 定位 | **去掉 line，只留文件名**——行号是最大漂移源，不如不要 |

</details>

## 第八步：人工通读

机器查不出"读起来像 AI 写的"。自己从头读一遍，专门找：

- 有没有句子在重复上一句的意思
- 有没有段落可以整段删掉而不损失信息
- 有没有解释了三遍同一个概念
- 加粗用了多少次（一页超过两处就砍）
- 有没有哪句是"正确的废话"

## 流程红灯 · 绝对不要做

这些是真实踩过的坑，每一条都导致过返工。

| # | 不要做 | 为什么 | 改成 |
|---|---|---|---|
| 1 | **把项目名/命令名写进模板正则** | 换个项目就抽不到内容，而且不会报错，只会静默失效 | 靠 `reference` 的 key 反向匹配，模板里不出现任何项目名 |
| 2 | **进度存储用全局 key** | 生成第二个项目时，两边进度串台 | 每个项目唯一的 `slug`，key 拼上 slug |
| 3 | **行内 code 加 `white-space:nowrap`** | 长变量名（`WEBHOOK_URL / WEBHOOK_METHOD`）会撑破布局，实测撑爆 3 页 | `overflow-wrap:anywhere`，代码块单独 `max-width:100%` |
| 4 | **入场动画从 `opacity:0` 开始** | 动画没跑完内容就不可见，截图和低性能设备上整页空白 | 只做位移，不改透明度 |
| 5 | **行内 code 样式不限定作用域** | `.opt code{...}` 会污染 `pre code`，代码块换行全丢，三行命令挤成一行 | 选择器精确到 `.opt .od code` 这种层级 |
| 6 | **参数表凭记忆手写** | 写出过官方文档里没有的选项（`--documents` 只在一条命令上有） | 只从签名生成，逐条回查 |
| 7 | **说「可以用 X 改」不说 X 是什么** | 新手分不清环境变量/CLI 参数/配置字段，改完没效果 | 首次出现点名：环境变量 / 命令行参数 / 配置文件字段 |
| 8 | **标题写数量不核对** | 写「三种东西」正文四条 | 落盘前数一遍，`verify.py` 会抓 |
| 9 | **为了凑形态造数据** | 空分类、无对位条目会让整页显假 | 抽到什么写什么，没有就留白并说明 |
| 10 | **不确定就写「大约」「通常」** | 无依据的量化比不写更糟 | 要么有实测，要么删掉 |
| 11 | **只抽「常用」的，说「其余看文档」** | 违背自足。用户来这里就是要全的 | 抽全，按用途分组；不确定总数先回去清点 |
| 12 | **覆盖度没到 95% 就说做完了** | 用户以为是成品，实际是半成品 | 明确说「这是第 N 册，还剩 X 项」 |


## 模块开关

| 模块 | 默认 | 什么时候开 |
|---|---|---|
| 正文 + 来源 | **必选** | — |
| 参考手册 | 自动 | `reference` 非空就显示 |
| 右侧速查 | 自动 | 同上 |
| 自测题 | 关 | 用户明确要检验掌握程度 |
| 破坏实验 | 关 | 用户有真实环境且愿意折腾 |
| 间隔复习 | 关 | 用户明确说要用很久 |

后三项不属于「内容自足」，不写它们不算遗漏。要开就问一句，不要擅自加。

## 交付规格

**每次都产出这些，缺一项就是没做完。**

| 项 | 要求 |
|---|---|
| 文件 | 每册一个 `index.html`（或 `part1.html`、`part2.html`），双击能开，无网络依赖 |
| 大小 | 单册 100–400 KB（40 页 / 300 条参考约 200 KB）。超过 500 KB 该拆册 |
| 内容 | `DATA` 填满：`slug`、`project`、`stages`、`reference`；分册时加 `series` |
| 覆盖度 | `coverage.md` 里没有「既没写也没写原因」的项；跑 `verify.py --coverage` |
| 校验 | `verify.py` 输出 `OK`，覆盖度 ≥ 95%（或 80–95% 且在 intro 说明） |
| 自检 | 三处硬编码（`<title>`、顶栏品牌、抽屉标题）已改成项目名 |

**页面必须具备的交互**（模板自带，不要删）：

- 左目录：全部阶段 + 当前阶段的步骤，标已读
- 一屏一页，`←` `→` 翻页
- 右侧速查：本页提到的参数，可展开
- `⌘K` / `/` 打开全量参考
- 页脚写明上一页/下一页的标题
- 进度存 `localStorage`，key 含 `slug`

**不确定时的默认动作**（不要停下来等回答）：

| 不确定的事 | 默认 |
|---|---|
| 层次 | 四层全要，按 L1→L4 排 |
| 版本 | 用最新稳定 tag，写进 intro 和每条来源 |
| 关数 | 依据覆盖度反推：条目多就多关、多册 |
| 参考条目 | **抽全**，按用途分组。不确定是否抽全就回去清点 |
| 可选模块 | 自测/破坏实验/复习关闭（它们不属于「内容自足」范畴） |
| 分册 | 按清点总数查表定册数（见第一步），先交付第一册 |

**先把能做的做完，把假设写在页面上**，比暂停等确认有用。用户看到成品才能给出有效反馈。

## 已知限制

- **行号会漂**。上游一改就失效。默认 `href` 指向文件而非行号锚点，`line` 仅作参考。
  查不到确切行号就只写文件名。
- **右侧速查靠 key 反向匹配正文**，会漏（正文用了别名）也会误（短词撞车）。
  匹配不到时右侧留白是正常的，不要造内容填。
- **非 Python 项目没有现成抽取配方**。Go、Rust、TS 见 `references/extraction.md`，
  没有的话自己 grep，别猜。

## 模板不写死的东西

这些都由数据决定，改数据就能变，不用改模板：

| 项 | 由什么决定 |
|---|---|
| 关数 | `stages.length` |
| 每关页数 | `steps.length` |
| 参考分类 | `reference` 里 `cat` 去重，没有就自动不显示 |
| 参考条目数 | `reference.length`，为 0 时按钮自动隐藏 |
| 进度隔离 | `slug`，每个项目必须不同 |
| 页面标题、品牌名 | `project` |
| 有无右侧速查栏 | 有 `reference` 才显示内容 |

**不要为了凑某个形态去造数据。** 项目没有 CLI 就没有"命令"分类，参考条目只有三条
就写三条。空分类、凑数条目会让整页显得假。
