# 学习引擎

## 最重要的一条：不许猜

**这份文档会被当成第一入口使用。写错一句，读者就会照着做错。**

写进去的每一句话，都必须是你验证过的。

| 级别 | 怎么算 | 能写吗 |
|---|---|---|
| **实测** | 你在本机跑过这条命令，看到这个输出 | ✅ 最好 |
| **源码** | 你在源码里读到这段实现，能指出文件行号 | ✅ 可以 |
| **文档** | 官方文档明确这么写，你能指出是哪一页 | ✅ 可以，但要标出来 |
| **推断** | 你觉得应该是这样，因为「一般来说」 | ❌ 不能写 |
| **记忆** | 你以前见过类似的用法，但这次没查 | ❌ 不能写 |
| **常识** | 大家都知道 X 是这样的 | ❌ 不能写 |

后三级是错误的主要来源。它们看起来很合理，读者也不会怀疑，但一旦错了，
读者会卡很久，而且不知道是文档错了。

**这些是真实发生过的**，每一条都不是「明显编造」，而是看起来对、实际错：

| 猜想 | 实际 |
|---|---|
| 「`holmes "问题"` 等价于 `holmes ask "问题"`」 | 只在完全没有参数时才自动补 ask，带参数会当成子命令名报错 |
| 「`--documents` 是 ask 的参数」 | 只有 `opsgenie` 一条命令有这个参数 |
| 「目录可以用 `HOLMES_CONFIGPATH_DIR` 改」 | 没说这是环境变量，读者会去配置文件里找，找不到 |
| 「工具输出动辄上万 token」 | 没有实测依据的量化 |
| 「FastAPI 没有 CLI」 | 有，`fastapi/cli.py` 提供 `dev` / `run` |

### 不确定的时候

只有三个选项，没有第四个：

1. **去查**。查源码、跑一遍、翻文档。这是默认动作。
2. **不写**。这一块空着，或者明说「这部分本文档没有覆盖」。
3. **标注不确定**。写「据官方文档 X 页，未实测」。

**不允许的第四种做法：写得像是确定的。** 用「通常」「一般」「大概」把不确定
包装成确定的，比不写更糟。

### 逐句自检

写每一段时停下来问：

| 写出来的句子 | 处理 |
|---|---|
| 「`docker stop` 默认等 10 秒」 | 有依据 → 留 |
| 「这个参数一般不太用」 | 没有依据 → 删，或改成具体的「什么时候用」 |
| 「性能会好很多」 | 没有量化 → 删，或补实测数字 |
| 「和 X 类似」 | 没说清哪一点类似 → 改成具体对比 |
| 「建议用 A」 | 补上具体值或场景 → 否则删 |

**看到「一般来说」「通常」「大多数情况」，停下来。** 这三个词是「我在猜」的信号。

**「建议」是好的，前提是给出具体值。** `建议把 --max-steps 设在 15–20` 是好句子；
`建议根据情况调整` 是空话。区别在于有没有替读者做决定。

**数字必须能数出来。** 标题写「三种方式」，正文就得恰好三条。

## 这个 skill 做什么

输入一个项目名和版本，输出**一份 HTML 读本**。

**唯一不管的是版本更新。** 本文档只对写它时的那个版本负责，明确写出版本号。
之后项目怎么变，不在这套文档的责任范围内。

**内容标准不是「够用」，是「有没有遗漏」**：

- 所有公开能力（命令、参数、API、配置项、环境变量）都要有
- 每个能力至少有一个能跑的例子
- 常见错误每个都要有对应解法
- 判断标准：读者遇到问题来这里查，**查不到就是缺陷**

**不存在「上手场景不读原理」这种豁免。** 层次决定顺序和篇幅，不决定写不写。

## 第一步：先定范围

**🔴 CHECKPOINT · 动手前停下**

三件事先定下来：层次、版本、深浅。**能从上下文推断的直接定，推断不出来才问。**

| 事项 | 能推断 | 推断不出来 |
|---|---|---|
| 层次 | 用户说「上手 / 二开 / 选型」→ 直接定 | 按默认四层全要，不再问 |
| 版本 | 本地仓库 / release tag → 直接查 | 按下面「版本三态」处理 |
| 深浅 | 用户说了时间预算 → 直接定 | 按默认：每章 4–6 节 |

**只有一种情况必须停下来问：用户的需求和项目本身不匹配**（比如要学的东西
根本不存在，或者他给的路径不对）。其余都按默认走，做完给他看。

### 1. 层次：默认全要

| 层 | 回答什么问题 | 位置 |
|---|---|---|
| **L1 用** | 我怎么让它跑起来 | 第 1–2 章 |
| **L2 懂** | 它内部怎么做到的 | 中间几章 |
| **L3 改** | 我要动它该从哪下手 | 靠后 |
| **L4 选** | 它和别的比强在哪 | 最后一章 |

**层次决定顺序和篇幅，不决定写不写。** 浅的在前、深的在后。

用户说「只要上手」时，**不是砍掉 L2–L4，而是把它们往后放**，
在 intro 里写明「第 3 章之后是原理，只想上手可以跳过」。

「深入一点」指的是 **L2，不是 L3**。用户想看内部怎么做到的，不等于想改它。
搞混了会把读本写成源码分析报告。

### 2. 版本：先钉，再谈别的

**动笔第一件事：查出版本号。** 查法见 `references/extraction.md` 的「先查版本」。

版本号写在**两处，缺一不可**：

1. **`intro` 第一段** —— 让从头读的人一开始就知道
2. **每条来源的 `why` 字段** —— 让从中间某页直接进来的人也能看到

第二处为什么也要写：读者可能通过链接直接跳到第 4 章，看不到 intro，
但会看到「本页依据」。

查不到版本就**明说「版本未知」**，并把「原理」章降级为「已知的设计取舍」。
不要随便写个「最新版」顶上。

### 3. 深浅：一晚上够用，还是准备泡一周

这决定每章放几节、每节写多细。用户已经说清楚了就别重复问。

**写不出阶段划分的理由，就按默认值走，不要停下来问。** 默认 = L1–L4 全要，
每章 4–6 节，每节 3–6 屏。

### 一本书，不是一套书

**最终产出永远是单个 `index.html`。**

不要把内容拆成 `part1.html`、`part2.html`。读者不需要知道「册」这个概念，
拆成多个文件会让他在文件之间来回跳，还会丢掉统一目录、统一进度、统一搜索。

**内容多怎么办：按章分。** 中等项目 6–12 章，大型 12–20 章。左栏是滚动的。
**单章不要超过 8 节**，超过说明该拆成两章。

### 先钉不可逆分叉

有些决策选错了要整页重做。写之前逐条定：

| 分叉类型 | 例子 | 选错的后果 |
|---|---|---|
| **大版本断代** | LangChain 0.3 `AgentExecutor` vs 1.x `create_agent` | 参数表、术语、示例全部作废 |
| **两套并存 API** | pydantic v1 vs v2、React 18 vs 19 | 一半内容对不上 |
| **部署形态** | 单机 CLI vs 服务端 vs Operator | 阶段划分完全不同 |
| **核心场景** | 用它当库调用 vs 当独立服务跑 | 整页重心偏移 |

自己判断出默认值（最新稳定版 + 最常见形态），写进 intro 和来源的 why。
**不要写「本页基于 X，如果你用的是 Y 请对照文档」**——那句话等于没说。

## 第二步：抽事实

**🔴 CHECKPOINT · 版本状态没定下来，不许开始**

不是「必须查到版本」——查不到也是一种状态，但你必须**明确知道自己在哪一种**：

| 状态 | 动作 |
|---|---|
| 查到具体版本 | 写进 intro 和来源的 why，正常写 |
| 只有大致范围（如 `4.x`） | 写进 intro，说明无法确认具体小版本 |
| 完全查不到 | 写「版本未知」，原理章降级为「已知的设计取舍」 |

三种都能开工。**只有「不知道版本、也没写清楚」这一种不能开工。**

按优先级取证据：

```
实测输出 > 源码 > 官方文档 > 二手资料
```

冲突时以更靠前的为准，并在正文里说明差异。比如文档写默认 60 秒，
但源码里 `DEFAULT_TIMEOUT = 20`，就以 20 为准，同时把矛盾写进正文 ——
读者可能拿着旧文档来对，你要先替他指出差别。

### 穷尽，不是挑选

**先做全量清点，再决定怎么写。** 抽事实的第一步不是挑重点，是把所有公开能力
列出来，记进 `coverage.md`。清点命令、格式、覆盖度算法见 `references/coverage.md`。

**边界和总数必须先有，具体条目可以边写边补。** 也就是说：动手前你得知道
「这个项目大概有 13 个命令、61 个参数、9 个环境变量」，但不必等这 83 项全部
查完才写第一章。

最低要求：

- 每项标 ✅ / 📝 / ❌，`❌` 必须写原因
- **最终交付**覆盖度 ≥ 95%（机器只在 < 80% 时硬拦，80–95% 出提醒 —— 提醒就得处理，别当没看见）
- **参数表只能从签名长出来。** 手写参数表是错误来源第一位

反例（真实踩过）：为了讲清 ripgrep 参数，agent 主动决定「旗标只取 30 个」。
按自足标准这是缺陷——全部都该进参考栏，只是分组呈现、正文只展开高频的。
**不要写死具体数字**，不同版本的参数数量不一样，写之前自己数。

**不要假设项目没有 CLI。** 很多库会附带一层薄 CLI（FastAPI 有 `fastapi/cli.py`
转发 `fastapi-cli`，提供 `dev`/`run`）。grep 过再下结论，否则会漏掉整个分类。

各语言的具体抽取命令见 `references/extraction.md`。

### 抽不到源码时

| 情况 | 处理 |
|---|---|
| 闭源 SaaS，无源码 | 只走文档路径，来源全标 `doc`，在页面顶部注明无法交叉验证 |
| 仓库太大（>10 万行） | 只读入口文件 + 公开 API 面，「原理」章改成「源码地图」 |
| 项目已停止维护 | 读最后一次 release 的 tag，在页面注明上游已停止维护 |
| 文档站打不开 | 读 README / 仓库内 docs，来源全标 `code`，在 intro 说明 |

## 第三步：设阶段

**不要固定四关。** 关数由项目复杂度决定，阶段名由项目自身结构决定。

判断依据是「学习者依次要回答的问题」：

1. 这东西是什么、为什么存在
2. 我怎么让它跑起来
3. 它内部怎么做到的
4. 边界在哪、细节怎么查

简单工具（jq、ripgrep）两个问题就够，两关。中等框架（LangChain）五关。
大型系统（K8s）五关。**要不要单独成关，看项目复杂度。**

层次会改变关卡：

| 层次 | 关卡怎么变 |
|---|---|
| L1 用 | 不要原理关 |
| L1 + L2 | 原理拆成 2–3 关，紧跟最小可用之后 |
| 加 L3 改 | 加「源码地图」和「扩展点」两章 |
| 加 L4 选 | 加一关对比，砍掉安装细节 |

**完成判据**：用一句话写出阶段划分的理由，并标明对应哪几层。
理由写不出来，说明还没想清楚，回第一步。

项目太简单凑不出 2 关时，合并成 1 关，页面就叫「全貌」。
参考条目 < 8 条时，**不要出读本**，出一屏速览。

## 第四步：建概念台账

**🔴 CHECKPOINT · 台账没排好，不许动笔写正文**

规模小的项目（≤2 章）可以只在脑子里过一遍，但**「这个概念在哪页第一次讲」
必须先有答案**。台账的载体可以是表，也可以是 intro 里一句话。

这是防止「前面看不懂后面」的唯一可靠办法。

人会不自觉地在讲 A 的时候提到 B，因为写的人已经懂了。读者按顺序读，
第一次遇到 B 时没有任何上下文，就卡住了。

### 怎么建

把整个读本里**所有会出现的概念**列成一张表。概念包括专有名词、命令与子命令、
配置项与环境变量、有理解门槛的参数、缩写。

对每个概念填四列：

| 概念 | 引入页 | 说明强度 | 后续使用页 |
|---|---|---|---|
| 镜像 | 1-3 | 完整（是什么 + 和容器的关系 + 图） | 2-2, 4-1, 4-2 |
| 容器 | 1-3 | 完整 | 全文 |
| `--rm` | 2-5 | 完整 | — |
| overlay 网络 | 5-3 | 一句话带过 | — |

**「引入页」必须是这一页的主题**，不是顺带提一句。
判断标准：这一页的小标题或标题里能出现它。

### 三条硬规则

**规则 1：引入必须先于使用。**

```
✗ 2-2 用 --rm 但不解释，2-5 才讲
✓ 2-5 讲 --rm，之后的页面才用它
```

`scripts/order.py` 会检查这一条。但**不要靠它**——它只能抓「标题里出现过」的术语，
抓不到纯叙述里的概念。

**规则 2：一个概念只引入一次。** 第一次出现的地方讲透，后面只调用不复述。

**规则 3：单页最多引入 4 个新概念。** 超过就拆页，或把概念挪到后面。
`order.py` 的阈值放宽到 6 才会报警——**4 是编辑标准，6 是机器兜底**，
两者不冲突：脚本只在明显塞爆时提示，具体压到几个由你判断。

### 台账存在哪

写进 `content.json` 同目录的 `concepts.md`，人可读。

**载体按规模变，判断标准不变：每个概念都得有明确的引入位置。**

| 项目规模 | 台账怎么做 |
|---|---|
| ≤ 2 章、术语 < 10 个 | 不写文件。在 intro 里用一句话交代概念顺序即可 |
| 3–8 章 | 写 `concepts.md`，完整四列表 |
| 9 章以上 | 写 `concepts.md`，且按章分组维护 |

台账的作用是让你自己看清顺序，不是交付物。它不进 `content.json`，
也没有脚本检查——所以别为了它写一堆用不上的行。

建台账的顺序：先列清单不排序 → 标出前置关系（B 依赖 A，A 放前面）→
按「它解决什么问题」分配到章 → 假设自己是新手，从第一页读到最后一页反查一遍。

不必写精确页码，写个大概范围就够——它的作用是让你自己看清顺序，不是给机器读。

## 第五步：写内容

**每写一页，先对照概念台账。** 用到的概念都在前面讲过吗？不在——要么挪到这页
来引入，要么换个说法绕开。**不允许「先用了再说，后面会讲」。**

写完一整章，回读一遍：假设自己只读过前面的章节，这一章有没有看不懂的地方。

### 每页的结构顺序

一页之内也要由浅入深，固定用这个顺序：

1. **这页解决什么问题**（第一段，会变成导语）
2. **最具体的例子**（一条命令、一张图、一个表）—— 先让读者看到东西
3. **它怎么做到的**（机制解释）
4. **坑和边界**（旁注或列表）
5. **和其他东西的关系**（对比表，可选）

**不要反过来。** 先讲机制再举例，读者会不知道你在说什么。

### 内容硬规则

- **术语首次出现给定义。** 不要假设读者知道 toolset、middleware、operator 是什么
- **配置入口首次出现必须点名类型**：`--flag` 是命令行参数，`UPPER_SNAKE` 是环境变量，
  `lower_snake` 是配置文件字段。不允许写「可以用 X 改」而不说 X 是什么
- **标出 experimental / deprecated**。官方标了就必须原样标
- **示例代码标明是示意还是真实输出**
- **一页最多两处加粗**

删掉 AI 腔：

| 别写 | 改成 |
|---|---|
| 值得注意的是、换句话说、总的来说 | 直接说结论 |
| 不只是 X，而是 Y | X 和 Y 分开讲 |
| 非常实用、极其重要 | 说清什么场景下有用 |
| 每段结尾都总结一遍 | 只在真需要回收时总结 |
| 强行对仗的四字标题 | 用具体名词 |

写法细节（代码块、表格、旁注、数字、反例）见 `references/writing.md`。

## 第六步：渲染

**你只写 `content.json`，渲染交给 `scripts/build.py`。不要手写 HTML，不要改样式。**

**命令里的 `<skill>` 换成这个 skill 的实际路径。** 内容文件用绝对路径或相对当前目录
的路径都行，产物生成在内容文件同目录的 `index.html`。

```bash
SKILL=~/.agents/skills/learning-engine      # 换成本机实际路径

python3 $SKILL/scripts/book.py check <内容>/content.json        # 结构 + 文风 + 顺序
python3 $SKILL/scripts/book.py build <内容>/content.json        # 校验通过才生成
python3 $SKILL/scripts/book.py all   <内容>/content.json --theme longread
python3 $SKILL/scripts/book.py all   <内容>/content.json --coverage <内容>/coverage.json
```

只有一个入口。`check` 失败即停，不用自己判断先修哪个。

**`content.json` 不要写进 skill 目录本身。** 放在你的工作目录，把路径传进去。

**`--theme` 不传就是 paper。** 上一轮用 longread，这一轮忘了传，
产物会被静默覆盖回 paper —— 所以每轮命令都带上 `--theme`，或者把命令记下来。

| 文件 | 管什么 | 谁改 |
|---|---|---|
| `content.json` | 全部内容 | **你** |
| `assets/templates/<theme>/` | 模板骨架 + 引擎 | 不改 |
| `assets/schema.json` | 数据结构约束 | 不改 |
| `assets/lint-rules.json` | 文风规则（词表、阈值） | **可改** |
| `scripts/` | 校验 + 生成 | 不改 |

**样式一致性靠这个流程保证，不靠 AI 记忆。** 你只产出 JSON，碰不到 HTML 和 CSS。

### 选主题

**🔴 CHECKPOINT · 主题定错了要重排版**

| 主题 | 参数 | 阅读方式 |
|---|---|---|
| **paper** | 默认 | 一屏一页，左栏目录，`←` `→` 翻页 |
| **longread** | `--theme longread` | 连续长文，一次滚到底，无侧栏 |

判断规则见 `references/theme-choose.md`。一句话版：
**用户说「查 / 对着做 / 手册」→ paper；说「读 / 通读 / 沉浸」→ longread；没说就用 paper。**

各主题的样式、尺寸、交互约定见 `references/theme-paper.md` 和
`references/theme-longread.md`——**只在排查视觉问题或新增主题时读**。

### content.json 结构

完整 schema 见 `assets/schema.json`。必填字段：

```json
{
  "slug": "docker",
  "project": "Docker",
  "version": "Docker 29.8.2 · Compose 5.5.0",
  "subtitle": "单机容器",
  "intro": "本读本基于……覆盖……不覆盖……",
  "sources": {
    "key": {
      "kind": "run | code | doc",
      "path": "docker --version | /path/file.py | docs url",
      "line": 123,
      "href": "https://...",
      "why": "这条支持了正文的哪个说法"
    }
  },
  "stages": [
    {
      "name": "章名",
      "desc": "一句话说明这章解决什么问题",
      "steps": [
        {
          "title": "节标题",
          "sources": ["key1", "key2"],
          "blocks": [ ... ]
        }
      ]
    }
  ],
  "reference": [
    { "cat": "分类", "key": "键名", "short": "一句话", "doc": "<p>详情</p>" }
  ]
}
```

### 硬性约束（build.py 会拒绝）

| 约束 | 值 | 为什么 |
|---|---|---|
| `slug` | 小写字母数字连字符 | localStorage 隔离 |
| `intro` | ≥ 40 字 | 必须写清版本、范围、不覆盖什么 |
| 每页 `sources` | ≥ 1 条 | 没有来源的页面不允许 |
| 每页 `blocks` | ≤ 12 个 | 超过说明该拆页 |
| 表格 | 每行列数 = 表头数 | 渲染会错位 |
| 角标 `{{n}}` | n ≤ 来源数 | 否则指向不存在的依据 |
| `sources[].kind` | run / code / doc | 三选一 |

### 块类型

**只有这十一种，写错类型名或漏必填字段，`check` 会直接拒绝**——
因为引擎认不出就静默输出空字符串，页面看着正常，实际整段丢了。

| type | 必填 | 可选 | 什么时候用 |
|---|---|---|---|
| `p` | text | — | 正文段落 |
| `h3` | text | — | 分节小标题 |
| `ul` / `ol` | items | — | 列表。有顺序用 ol |
| `note` | text | label | 要点旁注 |
| `warn` | text | label | 警告旁注 |
| `code` | code | lang | 代码块 |
| `table` | head, rows | — | 并列对比。有先后顺序用 ol |
| `kv` | items | — | 键值对，适合参数说明 |
| `split` | items | — | 2–4 个概念对比 |
| `opts` | items | unit | 多个可选方案；每项支持 title/desc/code/lang/note/pick/tag |

正文里 `{{1}}` 渲染成角标，对应本页 `sources` 数组第 1 条。

**行内强调用 HTML：`<strong>` 加粗、`<code>` 标代码。** Markdown 的 `**` 和反引号
不解析，会原样显示。`order.py` 抽术语只认 `<code>`，不写术语就抽不到，
顺序检查等于空过。

`reference[].cat` 去重生成分类，不要预设。项目没有 CLI 就没有「命令」分类，
不留空分类。

## 第七步：机器校验

**🔴 CHECKPOINT · 校验不通过不许交付**

```bash
python3 $SKILL/scripts/book.py check content.json                    # 结构 + 文风 + 顺序
python3 $SKILL/scripts/verify.py index.html --expect content.json     # 产物无损
```

两个都过，才算可以交付。详细检查项和失败处理见 `references/checks.md`。

最低要求：

- 每个 `path:line` 打开后内容对得上
- 每个 `{{n}}` 的 n 不超过该页 sources 长度
- 标题里的数字等于实际条目数
- 所有页面能渲染，零 JS 报错
- 窄屏无横向溢出
- 没有无来源的事实陈述

**脚本只能拦住形式问题。** 内容对不对，脚本判断不了——比如「`--max-steps`
默认 100」这个数字错了，脚本发现不了，只有你回查源码才能发现。

所以脚本是兜底，**真正的保证是开头那条：不猜。**

## 第八步：人工通读

机器查不出「读起来像 AI 写的」。自己从头读一遍，专门找：

- 句子在重复上一句的意思
- 段落可以整段删掉而不损失信息
- 同一个概念解释了三遍
- 加粗超过两处
- 「正确的废话」

## 流程红灯

真实踩过的坑，每条都导致过返工。

| # | 不要做 | 为什么 | 改成 |
|---|---|---|---|
| 1 | **参数表凭记忆手写** | 写出过官方文档里没有的选项 | 只从签名生成，逐条回查 |
| 2 | **说「可以用 X 改」不说 X 是什么** | 新手分不清环境变量/CLI 参数/配置字段 | 首次出现点名类型 |
| 3 | **标题写数量不核对** | 写「三种东西」正文四条 | 落盘前数一遍 |
| 4 | **为了凑形态造数据** | 空分类、无对位条目会让整页显假 | 抽到什么写什么，没有就留白 |
| 5 | **只抽「常用」的，说「其余看文档」** | 违背自足，用户来这里就是要全的 | 抽全，按用途分组 |
| 6 | **覆盖度没到 95% 就说做完了** | 用户以为是成品，实际是半成品 | 明说「已写 X 章，还剩 Y 项」 |
| 7 | **把项目名写进模板正则** | 换个项目就抽不到内容，且静默失效 | 品牌名只走 `{{PROJECT}}` |
| 8 | **进度存储用全局 key** | 生成第二个项目时两边串台 | key 拼上 `slug` |

## 交付规格

**每次都产出这些，缺一项就是没做完。**

| 项 | 要求 |
|---|---|
| 文件 | **一个 `index.html`**，双击能开，无网络依赖 |
| 大小 | 参考值：10 章约 120 KB，20 章 / 500 条参考约 400 KB。低于 40 KB 多半是内容太薄；超过 800 KB 说明有冗余 |
| 内容 | `DATA` 填满：`slug`、`project`、`version`、`stages`、`reference` |
| 覆盖度 | `coverage.md` 里没有「既没写也没写原因」的项 |
| 校验 | `book.py check`、`verify.py --expect` 都过；带 `--coverage` 跑一次，≥95% 才算交付 |
| 交互 | `⌘K` 开参数速查；进度和字号存 `localStorage`，key 含 `slug` |

**不确定时的默认动作**（不要停下来等回答）：

| 不确定的事 | 默认 |
|---|---|
| 层次 | 四层全要，按 L1→L4 排 |
| 深浅 | 每章 4–6 节，每节 3–6 屏 |
| 版本 | 能查到就用最新稳定 tag；查不到就写「版本未知」，不编一个顶上 |
| 章数 | 依据覆盖度反推，都在同一个文件里 |
| 参考条目 | **抽全**，按用途分组 |
| 分轮 | 内容多就分几轮，但每轮都在同一个 `content.json` 上追加 |

**先把能做的做完，把假设写在页面上**，比暂停等确认有用。

### 分轮写，但只有一本书

内容多的时候一次写不完，可以分几轮。**但每轮都在往同一个 `content.json` 里追加，
不是生成新文件。**

**轮次按章数定，不是固定三轮：**

| 总章数 | 怎么分 |
|---|---|
| 1–3 章 | 不分轮。写完一次交 |
| 4–8 章 | 两轮：前半 / 后半 |
| 9 章以上 | 三轮：第 1 轮写前 3–5 章，第 2 轮中间几章，第 3 轮剩余 |

**第 1 轮结束就 build 一次交给用户看。** 不要等全部写完才给第一眼 ——
清点可以边写边补全，第一章出来以后用户的反馈比一份完整的 coverage 表有用得多。

**🔴 每轮开始前先读一遍已有的 `content.json`。** 否则会忘掉前面用了哪些术语、
定过哪些约定，写出来的东西和前面接不上。

## 脚本与参考

全部在 `scripts/`，零依赖标准库。`book.py check|build|verify|all` 是统一入口，
它会按顺序调 `build.py` / `lint.py` / `order.py`：

- **`build.py` 是硬闸门**，结构错（字段缺、类型错、角标越界）就停
- `lint.py` / `order.py` 报「!」是建议，不阻断。它们的判断带主观性，
  卡死会逼你为了过检查去改内容 —— 那比不改更糟。**但建议要看**，
  尤其是「声称三种实际四条」这种硬伤，`lint.py` 会算作 error。

| `references/coverage.md` | 清点、覆盖度算法、分轮节奏 |

| `references/writing.md` | 代码块、表格、旁注、数字的具体写法 |
